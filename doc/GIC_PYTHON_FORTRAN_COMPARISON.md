# Python vs Fortran GIC Comparison

Date: 2026-06-20

This comparison checks whether the current Python GIC generator and the
Fortran77 GICForge backend produce compatible coordinate families. Exact line
counts are not expected for every molecule because Python and Fortran use
different non-redundant bases for some ring subspaces.

## Cases Checked

| Case | Python result | Fortran result | Notes |
| --- | --- | --- | --- |
| C4 chain | 3 stretches, 2 bends, 1 dihedral | 3 stretches, 2 bends, 1 dihedral | Direct match in families and counts. |
| THF test geometry | stretches, bends, CVB/CTor, 2 `RPck`, 1 `QPck`, 1 `PhiP` | stretches, `SymD`/`Rock`, `RDef`, 2 `RPck`, 1 `QPck`, 1 `PhiP` | Puckering functional coordinates are present in both. Auxiliary ring bases differ by design. |
| CO2 | stretches and linear-bend basis from Python primitives | stretches plus `LAng`/`LGIC` in Fortran | Fortran `SYMMALL` now preserves Gaussian output generation for linear bends. |
| C5H5 planar ring | Python `gblock` currently raises a shape-mismatch in `valence_angle_u` | Fortran writes `RPck/QPck/PhiP` with and without `SYMMALL` | Python bug is independent of GICForge and should be fixed in the Python transform layer. |

## Fortran Findings

- Initial GIC generation is structurally sensible: primitives are generated by
  coordinate family, ring coordinates are added before reduction, and final
  redundancy removal is type-local.
- `SYMMALL` must not generate coordinate combinations that the Gaussian writer
  cannot serialize. OOP combinations are therefore intentionally not invoked by
  the GICForge driver yet.
- A legacy format mismatch in the linear-bend report/writer path was exposed by
  CO2 with `SYMMALL`; it is fixed in `fortran/gicforge/mksalc.f`.

## Current Policy

Use Python for richer topology-aware grouping and workflow orchestration. Use
GICForge for Cartesian-to-GIC construction, type-local optional
symmetrization, type-local residual B-rank pruning, readable reports and
Gaussian input generation.
